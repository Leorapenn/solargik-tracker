# CLAUDE.md

Hard rules for this repo. These apply to everything below, not just the code that existed when they were written.

## Database

- This project uses a hosted **Neon Postgres** database via `DATABASE_URL` in `.env`. There is no local database.
- Never create a `docker-compose.yml`, local Postgres container, or any local database setup. If a task seems to need one, stop and ask instead.
- `.env` holds real secrets and must never be committed. `.env.example` lists variable names only, no values.
- The data model lives in `prisma/schema.prisma`. Treat it as given — if something in it looks wrong, say so and ask rather than changing it silently.

## monday.com

- This repo reads from monday.com. It must **never write back to monday.com** — no mutations, no column updates, no item creation, under any circumstances. All monday.com access is read-only GraphQL queries using `MONDAY_API_TOKEN`.
- The importer (`src/scripts/import-monday.ts`) always takes an explicit list of customer names or project codes as arguments. It must never default to importing every customer/project on the board.
- The importer must be safely re-runnable: match existing rows on `mondayItemId` and update them, never create duplicates.
- Customers board: `7980663322`. Supply Projects board: `6272830165`. Control Table board: `5738893445`.
- The project-to-customer link is the board_relation column `board_relation2__1` on Supply Projects. The `dropdown__1` Customer column on that board is a separate, conflicting list — do not use it for linking.
- Contract value, capacity, and country are read directly from the Control Table board (`5738893445`), not from mirror columns on Supply Projects — those mirror columns are not readable through the monday API (they return as an unsupported type).
- Customer name resolution goes through `Customer.name` and `CustomerAlias` only. Anything that doesn't resolve creates an `ImportReviewItem` and must **not** create a new `Customer` row.

## Stage 1 (done)

Schema, seed, `createProject` service, monday.com importer, read-only `/import` review page. No UI beyond that was in scope.

## Stage 2 (current)

- Navigation follows the Solargik 360 mockup (`Solargik 360.pdf` in Leora's OneDrive Documents folder): tabs are **Customers → Projects → Phases**. `/` redirects to `/customers`.
  - `/customers`: customer roll-up (project count, phase spread, editable `Customer.importance`, flags derived from aliases and blocked phases). `/customers/[id]`: that customer's projects plus Commercial / Name variants cards.
  - Tabs show the *type* of page, not the path taken: `/customers*` → Customers, `/projects*` → Projects, `/phases` → Phases. Breadcrumbs match the active tab (project page: `Projects › project`, with the customer as a link in the subtitle).
  - `/projects` and `/projects/[id]`: people edit **sub-stage** status only (`NOT_STARTED/IN_PROGRESS/BLOCKED/DONE`) via a server action. **Phase status is derived, never edited by hand**: `derivePhaseStatus` in `src/lib/phaseStatus.ts` (all done → DONE; any blocked → BLOCKED; any started/done → IN_PROGRESS; else NOT_STARTED) and is recomputed in the same locked transaction as every sub-stage change. Phases still don't gate each other. `npm run phases:sync [-- --dry-run]` re-derives every phase after a rule change.
  - **Project lifecycle** (`Project.lifecycle`: ACTIVE / PRE_NTP / ON_HOLD / SUSPENDED / CANCELLED) is derived by the importer from the Control Table `stage` and `status` columns via `deriveLifecycle` in `src/lib/lifecycle.ts` (first match wins: Status "Cancelled" → CANCELLED; STAGE "Suspended" → SUSPENDED; Status "Stuck/On Hold" or STAGE "7 Hold" → ON_HOLD; STAGE "0 Pre NTP & Pre AP" → PRE_NTP; else ACTIVE). A project's Control Table row can be linked from either board (Control Table `board_relation_mkwstnz6`, or Supply Projects `connect_boards6__1`/`board_relation_mkws6ea9`); the importer follows both. The raw labels are stored in `mondayStage`/`mondayStatus`. The status is also a dropdown (`ProjectStatusSelect`, action `setProjectLifecycle` in `src/server/actions/edit.ts`) on `/projects`, the customer page and the project page: changing it by hand locks `lifecycle` so the importer won't revert it (the project editor's "Use monday.com's value again" unlocks). It only refreshes when the importer is re-run. Shown as a badge on `/projects` (with filter chips and counts), the project page and the customer page; cancelled rows are dimmed and struck through.
  - **Dates, owners, history** (per sub-stage): `targetDate` (set by hand), `startedAt` / `completedAt` (recorded automatically when status changes via `applyStatusToDates` in `src/lib/subStageDates.ts`: In progress sets start; Done sets completed and a start if missing; reopening clears completed; Not started clears both; "today" is the calendar date in `APP_TIMEZONE` = Asia/Jerusalem), and `ownerId` → `Person`. Every status change also writes a `StatusEvent`. All writes go through `patchSubStages` in `src/server/services/subStages.ts` (locks the phase rows, re-derives phase status). Items marked Done before dates existed show "⚠ add date" until filled in. Phase cards and the Phases tab roll these up (`src/lib/phaseRollup.ts`).
  - **People** (`/people`, a tab): `Person` list + `DepartmentOwner` default owner per department. `createProject` gives new items their department's default owner; the "assign defaults" button fills items that have none. Owners are free to be added by hand now; the default-owner mechanism is the intended automation for new projects.
  - **Multi-select / bulk edit**: tick items on a project page (or whole phases on the Phases tab, which applies to every item in them) and change status, owner or dates at once (`updateSubStages` / `updatePhases` in `src/server/actions/updateStatus.ts`).
  - **Column filters on the project page** (`ColumnFilters` "+ Filter", logic in `src/lib/rowFilters.ts`): every column of the items table can be filtered via the URL (`phase`, `q` sub-stage name, `dept`, `owner` incl. `none`, `target`/`started`/`completed` = set/none/na (+ overdue for target), `status`); values within a column are alternatives, columns combine with AND. They combine with sorting and are included in saved views. The phase cards follow only the department filter. Header was tidied (flags inline, phase explanation collapsed, "Select items…" dropdown).
  - **Department filter and saved views**: `?dept=FINANCE,DESIGN` (helpers in `src/lib/departmentFilter.ts`, `DepartmentFilterBar` on `/phases`; on the project page it is one of the column filters) shows/counts only those departments' items (phase status, dates, owners are re-derived from just those items; phases with none are blank/hidden). Bulk edit on `/phases` under a filter changes only those departments' items (`updatePhases(phaseIds, input, departments)`), never the whole phase. "My views" (`SavedViews`, in the Sorted-by bar of every table; helpers in `src/lib/savedViews.ts`) saves the page's whole current query (sort, department, status filters) under a name in the browser's localStorage: private to that browser, no database, never alters the main view. Views are per page type (all customer pages share one list, all project pages another).
  - **Flags** (`Customer.flags` / `Project.flags`, string lists): short labels added and removed by hand with `FlagsEditor` on the customer and project pages (rules in `src/lib/flags.ts`: max 12 each, 40 chars, no case-insensitive duplicates; logic in `src/server/services/flags.ts`, auth'd actions in `src/server/actions/flags.ts`). **Customer flags are green / yellow / red** (`Customer.flagColors` JSON map label→color, default yellow; pick the color when adding, click a chip's dot to cycle it; the Flags column sorts red first); project flags are plain labels. Shown as chips in the Flags column of `/customers` (alongside the automatic name-variant / blocked chips) and `/projects`, and under project names on the customer page. Not imported from monday.com and never touched by the importer.
  - **Dates can be N/A**: `SubStage.naDates` / `SubStageTemplate.naDates` list the date fields (`targetDate`/`startedAt`/`completedAt`) that don't apply to an item (Contract Signing has no target date: set in `prisma/seedData.ts`, copied to new projects by `createProject`). Patch value `NOT_APPLICABLE` ("NA") sets the flag and nulls the date; a real date or Clear removes it; automatic start/completed dates are skipped for an N/A field and a Done item with an N/A completed date isn't flagged "no date". Dates are entered with `DateField` (`src/components/DateField.tsx`, helpers in `src/lib/dateInput.ts`): type DD/MM/YYYY (4-digit year required, auto-slashes), only a complete valid date commits (Enter/blur); the calendar popover never selects anything while changing month/year, only clicking a day (or Today / Clear / N/A) does. No native `<input type="date">`.
  - **Sorting and filters**: every table is sortable from its header row, by several columns at once: click = sort by that column only (toggle asc/desc); Shift/Ctrl/Cmd+click adds it as a further level (max 4); a "Sorted by" bar (`SortSummary`) at the top of each table card lets levels be removed. The choice is in the URL (`?sort=col:asc,col2:desc`; legacy `?sort=&dir=` still parses; helpers in `src/lib/sort.ts`, `SortTh`/`SortLink`). The status filter chips (`?lifecycle=`) are on `/projects` and each customer page and keep the current sort.
  - **Customer profile** (`/customers/[id]`): contacts imported from the Supply Projects POC 1-4 columns (`Contact`, one row per project and slot; the same person on several projects is shown once, see `src/lib/contacts.ts`; the card doesn't list which projects they're on), plus manual contacts. Importer also sets `Customer.importance` from the Customers board "Customer Importance" column.
  - **Edit buttons and the importer** ("your edit wins"): editing a monday-sourced field by hand (project name/country/capacity/contract value/status, customer name/importance) adds it to `lockedFields`; `planProjectUpdate`/`planCustomerUpdate` in `src/lib/importMerge.ts` never overwrite locked fields, and hand-edited contacts are `locked`. The editors offer "Use monday.com's value again" to unlock (value refreshes on the next import). The site never writes back to monday.com. Server actions return `UserError` messages as results (`src/lib/errors.ts`) because Next hides thrown error text in production.
  - `/phases`: matrix of every project × the six phases (status, start/completed/due date, owners), with a summary card per phase.
  - `/search?q=`: name search over customers (incl. aliases) and projects, from the top-bar box.
  - `/import` (review queue) is no longer a tab; it is reached from the "Missing customer link" tile / banner on `/customers`.
- Mockup items intentionally NOT built because the data doesn't exist: Payments tab, invoicing/"Ready to invoice", standing decisions, open commitments, last-sync time.
- Access is gated by one shared password (`APP_PASSWORD`, min 10 chars): `src/proxy.ts` redirects unauthenticated requests to `/login`, and every page and Server Action also re-checks the session (`src/lib/auth.ts`). The app is deployed publicly on Vercel, so never add a route, page or action without these checks. If `APP_PASSWORD` is missing the app fails closed.
- `/import` supports resolving a review item into an existing or new `Customer` (creating a `CustomerAlias` from the raw reference so future imports resolve automatically). Resolving deletes the `ImportReviewItem` — the fix takes effect on the next importer run, not retroactively.
- No styling framework — keep it plain/functional, consistent with Stage 1.
